01

先看整体：这条流水线在解决什么

Toonflow 不是"输入剧本、点一下出片"。它把 AI 短剧的失控点（角色漂移、越轴、镜头雷同、跨段跳变、审核被拒）逐个前置成一个可验收的文本环节，等所有约束都锁死了才开始烧钱生成图和视频。

  • 先文本、后图像、最后视频 — 画布分三排：前 7 个是纯文本决策，中间 5 个是分镜与图像，后 5 个是生成与交付。toonflow-canvas-template.ts:24
  • 每个环节都要人工验收 — 生成完进入"待验收"，你点通过它才变 approved，下游才允许开跑。
  • 约束一次锁死、后续只引用 — 风格、调色、布光、运镜基调在「分镜决策锁定表」一次锁定，后面所有环节都是引用它，不重新发挥。
  • 钱在闸门后面 — 一键跑全链时，第一次遇到图像环节弹一次成本确认，第一次遇到视频环节再弹一次；返修超过全片 20% 镜头也要再确认。
  • Agent 是操作者不是导演 — 画布侧的 Agent 拿到的是"这个环节的方法论红线"，它替你改内容、摆节点、触发生成，但改不了上面这些硬规则。

03

三段流水：文本 → 图像 → 视频

节点在画布上按这个顺序首尾相连（模板默认是一条链）。真正的分水岭是第 08 步：分镜表一旦通过验收，画布会"炸开"成按段并列的多条支线。

  1. 第一排 · 前期文本决策（01-07）
    全部纯文本 零成本

    剧本进来，先把"这片子长什么样"全部谈完：资产锚点、空间轴线、跨段继承、全局风格。这一排跑完，后面所有环节都只是在执行，不再做审美决策。这也是为什么锁定表叫"锁定"——A 表锁全片风格/调色/布光/运镜基调/表演档位，B 表逐段锁构图与景别跨度。

  2. 第二排 · 分镜与图像（08-12）
    结构化 JSON 首次烧钱

    分镜表把剧本切成"段 + 镜"，每段贴满 12-15 秒、每镜 3-5 秒。镜头合同和动作合同逐镜补细节。故事板页把一段画成一张多格灰模图——它只锁镜序与构图，刻意不传任何参考图，防止角色/装备细节污染粗模。

  3. 第三排 · 生成与交付（13-17）
    大额成本 人工验收

    过审做一遍避雷词清洗，视频工作台按段生成视频（必须以该段故事板页为构图锁），接缝检查验跨段连续性，音频混音铺配音/BGM/SFX，最后导出。

04

分镜表通过之后：画布按段炸开

这是整条流程里最容易看不懂的一步。前 10 个环节全片各一个节点，从第 11 步开始变成"每段一套"。instances.ts:5-6, 55-59

触发条件

分镜表必须先 approved

只有分镜表节点状态是 approved、且产物本身也是 approved 时才会同步实例。没验收就没有段。instances.ts:59

派生对象

每段派生 3-4 个节点

故事板页 · 视频工作台 · 音频混音（画布上有该根节点才建），外加已退役的首帧。节点标题形如「故事板页 · 段1」。instances.ts:131-132

改表之后

差异同步，不是重建

改了分镜表重新验收，系统算出新增 / 失效 / 归档三份清单，弹窗让你确认再落地——不会默默删掉你已经生成好的段。

段的物理含义

一段 = 一次视频生成

12-15 秒的上限来自视频模型单次生成能力。段内的镜头切换由模型在一次生成里原生完成，天然连贯；只有段之间才是真的"缝"，要走缝合同。

状态机、级联、成本闸门

每个节点共用一套七态状态机，"一键向下重生成"沿拓扑序严格串行执行。

七个状态与合法迁移 
empty ──generate──> generating ──成功──> review ──通过──> approved
                        └──失败──> failed ──重试──> generating

上游出新版本 → 下游自动变 stale（需重跑）
选修环节初始为 skipped，点一下即启用

schema.ts:4-14, state-machine.ts:153-179。generating 是唯一不允许再次进入生成的状态——重复点按钮会被状态机挡掉。

级联为什么是串行的（不是能力不够，是踩过坑）

「一键向下重生成」用一个 for 循环走拓扑序，一次只跑一个节点cascade.ts:62，并且同时只允许一条级联在跑project.tsx:3662。

原因写在代码注释里：下游节点准备输入时读的是内存快照，背靠背并行调用时 React 还没提交上一个节点的结果，下游会拿到旧版本并把新结果冲掉。实测现象是空间合同的"待验收"被分镜表的准备快照冲回"生成中"。project.tsx:2868-2870

另一个原因是成本要按批算——并行就没法在跨入图像/视频边界时统一弹确认。

三道闸门分别在哪
  • 图像闸门 — 级联第一次遇到图像类环节时弹一次，列出本次会烧掉的所有图像节点。cascade.ts:73-78
  • 视频闸门 — 第一次遇到视频类环节时再弹一次。cascade.ts:79-84
  • 返修 20% 闸门 — 质量检查后提返修计划时，如果预计重做的镜头数超过全片总镜头数的 20%，先把范围和成本摆给你看。注意分母是全片不是本段（2026-07-27 对抗审查纠正过一次：按本段算的话「4 镜里改 1 镜」会显示 25%，而全片其实只有 1/40）。node-runtime.ts:153-177
06

质量红线：机器能判的部分不靠人眼

分镜表生成后会跑一遍结构化检查，把"镜头长得都一样"这类问题在图像生成之前就拦下来。

四维多样性

运镜 / 景别 / 角度 / 构图

每段运镜 ≥2 种、景别跨度 ≥3 档且含极值 L0 或 L5、角度 ≥2 种、构图主策略 ≠ 次策略。连续 3 镜同景别、连续 3 镜同运镜直接判不达标。

短段保护

凑不出来的不算不达标

一段只有 2 镜时物理上凑不出 3 档景别，这种情况标 unknown 而不是 fail，避免冤枉合法的短段。quality-check.ts:27-30, 334-338

高潮镜三件套

缺一不许输出

爆点镜必须同时有：L5 五部位动作编码、Speed Ramp 四要素、景别只能取 L4/L5。字段落点固定，供下游机械识别。prompts.ts:239-243

封闭词库

只许抄，不许自创

导演风格 9 种、调色 22 组、布光 10 方案、运镜 8 种、P7 技法九类——全部逐字选取，禁止改名、简写、拼接。closed-libraries.ts

参考图什么时候传、什么时候刻意不传

这块最容易被误认为是 bug，单独拎出来说。全部逻辑集中在一个函数里，Agent 触发和手点按钮走的是同一条路。node-runtime.ts:361-416

环节参考图行为为什么
故事板页刻意不传纯文生图，referenceKeys = []blockout 只锁构图与体块，传角色/装备/色板参考会把不该出现的细节带进粗模
首帧（已退役）强制必传故事板页线稿设为 mandatory，读取失败直接中止线稿是构图锁，只上色不改构图，不得退化为文生图
视频工作台强制必传找不到该段故事板页就抛「请先生成该段故事板页」视频必须基于 Module3 故事板页
资产锚点卡有则跟随有参考图时以参考图为唯一形象基准锚点卡本身就是后续所有环节的形象来源

音频卡会被主动从图像参考里剔除——它的 storageKey 是音频媒体键，混进来会当图像读取失败。node-runtime.ts:381-383

08

Agent 在这条流水线里干什么

画布右侧的 Agent 面板背后是 canvas-agent 服务，它把画布暴露成 24 个工具给模型调用。它是操作者，不是决策者。

能做

读画布、改内容、触发生成

取全画布或选中节点的状态、创建/更新/移动/连线/删除节点、直接调起文生图/图生视频/TTS、跑既有生成流。

方法论注入

按环节发红线，不是发全文

Agent 看到画布上有 Toonflow 环节时会拿到一份总纲，改具体环节前再取该环节的方法论红线。工具调用返回时会在边界处重新注入，防止多轮对话把方法论聊忘。canvas-agent/src/methodology.ts

本地能力

读本地文件、ffmpeg 拼接

Agent 能读本机图片转 dataURL 送进画布；成片阶段可调本地 ffmpeg 做无损拼接，不重编码。

改不了

硬规则不归 Agent 管

参考图组装、状态机迁移、成本闸门、质量红线都在画布代码里。Agent 只能触发生成，改不了这些规则——所以"某环节没带参考图"这类现象要去看环节定义，不是看 Agent。

已知缺口（本次排查发现，尚未修）

下面三条是查这条流程时顺带确认的真问题，跟流程设计无关，属于实现缺陷。

  • 生成完成后节点被压回原高度 — 流式生成时节点临时撑到 440px，跑完无条件还原到生成前的高度（模板默认 190px）。结果就是过程看得见、产物反而看不见。streaming.ts:76
  • 生成期间手动调高会被吞掉 — 还原用的是生成开始前记录的旧值，不是你改后的当前高度。streaming.ts:51, 76
  • 并行生成时"停止"按钮会丢 — 运行态是单值 state，先跑完的那个会把它清空，另一个节点的停止按钮跟着消失。实际并行跑了，只是 UI 跟不住。project.tsx:408, 2854, 2889
