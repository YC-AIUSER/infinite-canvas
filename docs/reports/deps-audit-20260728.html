01

摘要

34 条里 25 条（74%）在这个项目的实际用法下走不通利用路径，多数是构建期/测试期才跑的工具链，或者代码里根本没调用到出问题的那部分。真正值得动手的是下面 3 条。

  • axios（web，高危，直接依赖） — 10 条通告集中在一个包上，且它是真正会带着用户配置的 API 地址、密钥去发请求的库。是直接依赖，修复版本现成，升级成本最低、收益最实在，排第一优先级。
  • dompurify（web，低危，经 mermaid ← streamdown 传递） — 严重级别虽然只是"低"，但这是本次审计里唯一一条查实了"确实会碰到 AI 生成内容"的链路：web/src/components/canvas/canvas-agent-chat-ui.tsx:55 用 Streamdown 渲染 Agent 聊天文本，Streamdown 内部靠 mermaid 画图表、mermaid 又用 dompurify 净化输出。如果 Agent 被提示注入诱导吐出恶意 mermaid 代码块，这条链路是理论上能被摸到的。优先级按"路径是否真实"排，不是按严重级别数字排。
  • vitest + vite + vite-node（canvas-agent，含 1 条严重级别） — vitest 那条是本次唯一的 critical：Vitest UI server 监听时可以被读取并执行任意文件。canvas-agent 的 test 脚本平时跑的是 vitest run（没开 --ui），风险不算火烧眉毛，但升级三个包一次搞定、成本很低，没有理由留着一个 critical 级别的通告不处理。
02

评估前提

判断"暴露面"离不开"这是个什么样的应用"。下面这段是评估的前提，逐条判断都基于它。

infinite-canvas 是纯本地单机应用：前端画布（web/，React + Vite，浏览器里跑，数据存 IndexedDB/localforage）+ 本地 Agent CLI（canvas-agent/，Node，跑在用户自己电脑上）+ 文档站（docs/，fumadocs/Next.js，只用于生成静态文档）。没有对外服务端：不接收公网请求、不处理多租户数据、没有服务器渲染的用户输入面。edge-relay/ 是可选的转发 Worker，本次审计范围外。用户是单人使用，攻击者要能利用漏洞，通常需要先能控制用户的输入内容（比如诱导打开恶意画布文件、让 Agent 处理恶意内容）。

已知事实：@ant-design/pro-components@3.0.0-beta.3 声明 peer antd@^5，项目实际用 antd 6，CI 里靠 --legacy-peer-deps 装 —— 升级 pro-components 时要注意这个兼容问题。

为了不让判断停留在"理论上可能"，逐项打分前先翻了一遍代码库，核实到以下几个直接影响判断的事实：

  • web 的 dev/preview 脚本绑定 0.0.0.0 — web/package.json 里 "dev": "vite --host 0.0.0.0 --port 3000"、"start": "vite preview --host 0.0.0.0 --port 3000"，开发/预览服务器会监听所有网卡，不是只有本机能连，这个背景信息在判断 vite/esbuild 类"需要访问到本地 dev server"的漏洞时要考虑进去（虽然本次给到的 web 侧 34 条里没有直接列出 vite/esbuild，这条是留给后续复审的背景注记）。
  • pro-components 的代码高亮链路实际没被用到 — web/src/components/layout/app-providers.tsx:3 只 import 了 ProConfigProvider（纯主题/Context Provider），没有引入 pro-components 里会渲染代码高亮的组件。这意味着 react-syntax-highlighter → refractor → prismjs 这条依赖链在这个项目里实际渲染代码路径从未被执行。
  • dompurify 真实经由 mermaid ← streamdown 引入 — web/src/components/canvas/canvas-agent-chat-ui.tsx:55 用 <Streamdown> 渲染 item.text（Agent 返回的聊天内容），这是本次审计里唯一确认"渲染路径可能接触到 AI 生成/外部内容"的一条，详见摘要。
  • @modelcontextprotocol/sdk 在 web 侧其实来自 shadcn CLI 工具 — web/package.json 里 "shadcn": "^4.7.0"（shadcn 组件脚手架 CLI），是它把 @modelcontextprotocol/sdk、hono、@hono/node-server 一起带进来的；web/src 全目录搜索不到任何地方 import 这三个包，说明它们只是"装了但没在应用代码里用到"的 CLI 附带依赖。
  • canvas-agent 的 MCP server 不走 HTTP/hono — canvas-agent/src/mcp-server.ts:14 用的是 StdioServerTransport（标准输入输出管道），不是走 HTTP 的 transport，hono 的 serve-static 那段代码根本不会被跑到。canvas-agent 自己对外的 HTTP 服务器（canvas-agent/src/http-server.ts）用的是 Express，不是 hono，并且在第 169 行显式 app.listen(port, "127.0.0.1", ...)，只监听本机回环地址。
  • canvas-agent 的 test 脚本不开 vitest UI — canvas-agent/package.json 里 "test": "vitest run && npm run test:session"，日常跑的是无 UI 模式；docs 的 next.config.mjs 设了 output: 'standalone'（理论上可以起 Node 服务器），但 docker-compose.yml／Dockerfile 里都没有把 docs 纳入实际部署的服务，目前确实只是本地 next build/next dev 使用。

建议处理顺序

按"实际风险 × 升级成本"排序，成本低、风险路径真实的排前面。

  1. 升级 axios
    web · 直接依赖

    10 条通告集中在一个包、是真正对外发请求的库、修复版本现成。跑一次 npm audit fix 或手动升级到最新 1.x patch，再确认当前锁定的 1.16.0 是否已完全覆盖这 10 条 GHSA。

  2. 升级 vitest（连带 vite / vite-node）
    canvas-agent

    唯一的 critical 通告，且是三个包一起升的一次性操作，成本很低，没有理由拖着。

  3. 处理 dompurify（经 mermaid）
    web

    严重级别低，但这是唯一确认摸得到"AI 生成内容渲染"路径的一条。升级 mermaid 或给 dompurify 加 npm overrides 都行，成本不高，值得顺手处理。

  4. 找用户确认 next / sharp 的部署形态，以及 fast-uri 的实际引入路径
    docs · web · canvas-agent

    这 4 条不是"不用管"，是"现在的信息不够下结论"。next/sharp 需要用户明确"docs 会不会真用 standalone 模式对外跑"；fast-uri 需要跑一次 npm ls fast-uri 定位引入路径和用途。确认完再决定升不升。

  5. 暂不动 @ant-design/pro-components 及其代码高亮链路
    web · 低优先级

    已确认这条链路的漏洞代码路径在本项目里没被执行，属于"无实际暴露可缓办"。如果以后因为别的原因（比如要用 pro-components 新特性）想升级它，要留意它声明的 peer 是 antd@^5，而项目实际用的是 antd 6，目前靠 --legacy-peer-deps 硬装——升级前要么继续用这个绕过参数，要么等上游把 peer range 放开到 antd 6，否则会撞包管理器报错。

05

未采取行动的说明

这次是评估，没有升级任何依赖、没有改任何代码。原因不是"怕出错走个流程"，是这份报告本身就改变了要不要动手的判断。

34 条 npm audit 通告如果直接一股脑 npm audit fix --force，会出两个实际问题：一是会升级掉 25 条这次查实"用不到"的依赖，这些依赖该不该动跟安全没关系，纯粹是不必要的改动风险（比如 pro-components 升级会直接撞上 antd6 的 peer dependency 冲突，得手动处理）；二是 next.js、vite/vitest 这类工具经常有跨大版本的破坏性变更，盲目升级可能把现在能跑的东西升坏，却换不来真实的安全收益。

所以顺序应该是：先把这份报告看完，挑出"建议升级"的 5 条动手（axios、dompurify、vitest 三兄弟），"需进一步确认"的 4 条找用户或者查一下代码定位清楚，再决定动不动。25 条"无实际暴露可缓办"的可以先放着，不用为了清空 audit 输出的红字而做无谓的升级。
